## 1. 이번 수정 내역 (v20)

### 1-1. 렌더 루프 (파이어폭스 끊김의 주원인)

- **문제:** 원본 코드는 `setTimeout` 66ms 간격(최대 15fps)이었고, 한 프레임이 33ms를 넘으면 66ms를 *추가로* 기다렸다. 그래서 그리기가 느린 브라우저에서는 프레임이 계단식으로 반토막 났다.
- **수정:** `requestAnimationFrame` 기반 루프로 바꾸고 목표를 33ms(30fps)로 했다. 다음 프레임을 먼저 예약하기 때문에 그리는 도중 오류가 나도 화면이 멈추지 않는다.
- **추가로 줄인 부하:** 행성 위치를 매 프레임 계산하던 것을 2초에 1번으로 줄였다. 센서 이벤트마다(초당 60회 이상) 화면 글자를 다시 쓰던 것도 값이 바뀔 때만 쓰도록 했다.

**측정 결과 (헤드리스 Chrome, 모바일 화면 크기, FOV 90°):**

| 조건 | 수정 전 | 수정 후 |
|---|---|---|
| 일반 CPU | 14 fps / 그리기 3.2ms | **30 fps** / 1.4ms |
| CPU 6배 감속 (저사양·파이어폭스 상황 모사) | **6 fps** / 27ms | **30 fps** / 12ms |

### 1-2. 센서 처리

- **자이로 없는 기기 버그:** `gyroListener`는 alpha(방위)가 null이면 기울기(beta/gamma)까지 갱신하지 않았다. 그래서 자이로가 없는 일부 저가 기기에서는 화면 전체가 멈췄다. 이제 alpha와 상관없이 기울기를 갱신한다. (테스트: alpha=null 상태에서 고도 45°→70° 정상 추종)
- **떨림 완화:** 카메라 전방 벡터에 시간 기반 저역통과 필터를 적용했다(시정수 70ms).
  - 오일러 각을 따로따로 평활화하면 360°↔0° 경계나 천정 근처에서 값이 튄다. 그래서 벡터 단위로 처리했다.
  - 15° 이상 갑자기 바뀌면(모드 전환·정렬 등) 필터를 거치지 않고 즉시 반영한다.
- **천정 NaN 방지:** 망원경이 천정을 향하면 수평 성분이 0이 되어 계산이 깨질 수 있었다. 이 경우 직전 방향을 유지하도록 했다.
- **화면 회전 보정:** 처음 검토할 때는 필요하다고 봤으나 적용하지 않았다. 코드를 다시 확인해 보니 이 앱의 시선 방향은 폰 상단 모서리(기기 Y축)로 계산되고, 좌우축은 시선 방향에서 수평으로 다시 계산된다. 그래서 화면이 가로로 돌아가도 하늘 방향이 뒤바뀌지 않는다.

### 1-3. 설치형 앱 / 서비스워커

| 문제 | 수정 |
|---|---|
| 등록 URL에 `?현재시각` → 실행할 때마다 새 워커 설치, 1.4MB 전체 재다운로드 | 고정 URL + `updateViaCache:'none'` |
| 캐시 우선 + HTTP 캐시 경유 → index.html과 js 버전이 섞일 수 있음 | 같은 출처는 **네트워크 우선(서버 재검증)**, 3초 안에 응답이 없으면 캐시 사용 (관측지 약전계 대응) |
| 어떤 요청이 실패해도 index.html로 응답 | 대체 페이지는 페이지 이동 요청에만 사용. 외부 요청(DSS·위키·통계)에는 관여하지 않음 |
| 설치 경로 하드코딩 | 워커 scope 기준으로 계산 (로컬 테스트도 가능) |

### 1-4. 기타

- **전체화면 토글:** 설치형 앱(fullscreen/standalone)이나 미지원 브라우저에서는 숨긴다. 이미 전체화면일 때 호출해도 예외가 나지 않게 막았다.
- **화면 켜짐 유지:** 다른 앱에 다녀오면 브라우저가 이 설정을 자동으로 해제한다. 이제 앱으로 돌아오면 다시 요청한다.
- **노치/홈바 영역:** `viewport-fit=cover`와 safe-area 여백을 적용했다. 아이폰 설치형 앱에서 상단 버튼이 상태바에 가려지던 문제, 가이드 버튼이 홈 인디케이터와 겹치던 문제를 해결했다.
- **진단 정보:** 설정창 하단에 `Chrome · App(fullscreen) · 센서 60Hz · 30fps · 2ms · 나침반 ON` 형식으로 표시한다. 현장에서 문제가 생기면 이 줄을 캡처해서 받으면 원인을 바로 좁힐 수 있다.
- **의도적으로 유지한 것:** 첫 줄의 `<!DOCTYPE>`는 비정상이라 브라우저가 호환(quirks) 모드로 동작한다. 하지만 원본 레이아웃과 캔버스 크기 계산(`body.clientHeight`)이 이 모드에 의존하고 있어서, 고쳤을 때의 위험이 이득보다 크다.

### 1-5. 디버그 검증 (자동 테스트, 수정 전/후 비교)

| 항목 | 수정 전 | 수정 후 |

## 2. 다음 작업 검토

### ① 위아래 드래그 (스텔라리움 방식)

**현재 구조**
- `moveSky()`는 가로 이동량만 `alpha_user_offset`(방위 오프셋)에 더하고, 나침반 모드에서는 무시한다.
- 고도는 항상 폰 기울기(beta/gamma)로 결정된다.

**핵심 판단: 센서가 고도를 제어하는 동안 위아래 드래그를 더하면 둘이 서로 싸운다.**
폰을 들면 위로 가고, 드래그하면 또 위로 가는 식이라 사용자가 헷갈린다. 그래서 스텔라리움처럼 **"탐색(자유 시점) 모드"** 를 따로 두는 것을 권장한다.

| 모드 | 방위 | 고도 |
|---|---|---|
| 망원경 모드 (현재) | 센서(+좌우 드래그 오프셋) | 센서 |
| 탐색 모드 (신규) | 드래그 | 드래그 |

**구현 방법**
- `getCameraRays()` 앞단에서 탐색 모드일 때 `fwd = [sin az·cos alt, cos az·cos alt, sin alt]`로 직접 만든다. 이후 lft/top 계산은 그대로 재사용한다.
- 고도는 ±89.5°로 제한한다(천정 처리는 v20에서 이미 보강함).
- 관성 스크롤(손을 뗀 뒤 감속하며 계속 이동), PC용 마우스 드래그·휠 줌은 선택 사항이다.
- 정렬(`align`)을 누르면 망원경 모드로 자동 복귀한다.

**난이도: 쉬움 (0.5~1일).** 시작 페이지의 모드 구조가 생기면 "탐색"을 경위대 모드 안의 토글로 넣으면 된다.

### ② AR 기능

**구성:** 후면 카메라 영상(`getUserMedia`) 위에 투명 캔버스로 별·별자리·대상 표시를 겹친다.
- WebXR(`immersive-ar`)은 안드로이드 크롬만 지원하고 iOS는 지원하지 않는다. 따라서 **getUserMedia + DeviceOrientation** 방식을 권장한다.
- HTTPS(GitHub Pages)이므로 카메라 권한 조건은 충족된다.

**현재 코드와 다른 점 (중요)**

| 항목 | 경위대(망원경) 모드 | AR 모드 |
|---|---|---|
| 시선 방향 | 폰 **상단 모서리**(기기 +Y) — 폰을 경통에 붙여서 사용 | 폰 **뒷면 카메라**(기기 −Z) |
| 화면 기울기(roll) | 수평으로 강제 | 폰 기울기를 그대로 따라감 |
| 화각 | 사용자가 선택(7~150°) | **카메라 실제 화각에 고정**해야 겹침이 맞음 |

→ `getCameraRays()`에 "축 선택" 분기만 추가하면 된다. 좌표 변환과 별 그리기 코드는 그대로 재사용할 수 있다.

**기술적 과제와 대응**

| 과제 | 내용 | 대응 |
|---|---|---|
| 카메라 화각 | 브라우저가 화각을 알려주지 않고 기종마다 다르다(대략 가로 60~75°) | 기본값 + 슬라이더 보정, 또는 "밝은 별 2개 맞추기"로 자동 보정 |
| 나침반 오차 | 휴대폰 지자기 센서는 ±5~15° 오차, 금속 근처에서는 더 커짐 | 기존 **1성 정렬** 기능을 AR에도 적용(별 하나를 탭해서 보정) |
| 야간 시력 | 카메라 미리보기가 밝아서 암적응을 해친다 | 영상 밝기 제한 + 적색 필터(CSS filter), 영상 끄기 옵션 |
| 밤에 카메라로 보이는 별 | 폰 카메라로는 밝은 별 몇 개만 보인다 | 실용 가치는 "어디가 어느 별자리인지" 안내. 황혼·도심에서 특히 유용 |
| iOS | 카메라와 방향 센서 권한을 각각 사용자 터치로 요청해야 함 | 시작 페이지의 "AR 모드" 버튼 터치에서 한 번에 요청 |

**권장 단계**
1. **AR-lite (1일):** 카메라 없이 폰 뒷면 방향으로 하늘을 보는 "스카이 뷰". 축 변경과 roll 반영만 하면 된다.
2. **AR (2~4일):** 카메라 배경 + 화각 보정 + 1성 보정 + 적색 필터.

**난이도: 중간. 가능성 높음.** 사용자 의견대로 경위대 모드와 같은 계산 경로를 쓰면 되고, 차이는 "축 선택"과 "화각 고정"뿐이다.

### ③ 시작 페이지

**구성안:** 어두운 배경, 앱 제목, 언어 선택, 모드 선택 3개(경위대 / 적도의 / AR)

```
        ✦ AstroHopper KR ✦
        [ 한국어 ▾ ]

   ┌───────────────────────────┐
   │  🔭 경위대 모드            │  돕소니안·경위대 — 바로 시작
   ├───────────────────────────┤
   │  🧭 적도의 모드            │  극축 정렬 → 탐색
   ├───────────────────────────┤
   │  📱 AR 모드                │  카메라로 하늘 보기
   └───────────────────────────┘
   ☐ 다음부터 이 모드로 바로 시작
```

**설계 포인트**
- **권한 요청을 이 화면에 모은다.** 모드 버튼 터치가 iOS 방향 센서 권한(`requestPermission`), 위치, (AR이면) 카메라를 요청하는 사용자 동작이 된다. 지금 따로 떠 있는 "센서 허용" 대화상자를 없앨 수 있다.
- 언어 선택은 기존 설정창의 `lang_select`를 그대로 연결한다(새 사전 불필요).
- 모드 상태는 전역 변수 `global_app_mode`('altaz' | 'eq' | 'ar')와 localStorage로 관리한다. 기존 퀵스타트는 모드 선택 후 해당 모드 안내로 보여준다.
- 설정창에 "모드 변경" 버튼을 넣어 시작 페이지로 돌아갈 수 있게 한다.
- 별도 파일 `js/start.js`(AHStart 모듈)로 분리한다. 대용량 index.html 수정을 최소화하고, 서비스워커 캐시 목록에 추가한다.
- 적색 테마 유지: 어두운 배경 + 붉은 글씨. 야간 시력 원칙에 맞게 흰색은 쓰지 않는다.

**난이도: 쉬움~중간 (1~2일).** 나머지 모든 작업의 출발점이므로 **가장 먼저** 하는 것을 권장한다.

### ④ 경위대 / 적도의 모드 — 극축 정렬 가능성 검토

#### 경위대 모드
현재 앱이 곧 경위대 모드이므로 시작 페이지에서 바로 연결하면 된다. 위아래 드래그(①)는 이 모드 안의 "탐색" 토글로 넣는다.

#### 적도의 모드 — 제안하신 "적경축·적위축만 돌려서 계산" 방식 검토

**결론: 원리적으로 타당하고, 폰 기반에서 현실적인 방법이다.**

**원리**
- 폰을 경통에 고정하고 적위 클램프를 잠근 채 **적경축만** 돌리면, 폰의 자세는 *적경축을 회전축으로 하는 회전*만 겪는다.
- 회전 전후 두 자세의 상대 회전 `R₂·R₁ᵀ`의 회전축이 곧 **마운트 적경축의 실제 방향**이다.
- 여러 샘플을 얻으면 시선 벡터들이 원뿔(원)을 그리므로, 그 원이 놓인 평면의 법선(최소제곱 평면 맞춤)으로 축을 더 안정적으로 구할 수 있다.
- 이 축을 천구 북극 방향(방위 0°, 고도 = 현지 위도)과 비교하면 **극축의 고도 오차와 방위 오차**가 나온다.

**이 방식의 큰 장점**
- 회전축 방향은 **폰을 경통에 어떤 각도로 붙였는지와 무관하다.** 장착 오차가 결과에 들어가지 않는다. 이것이 "축만 돌리기" 방식의 핵심 이점이다.
- 별을 보지 않고 낮이나 초저녁에도 대략적인 극축 점검이 가능하다.
- 적위축도 같은 방법으로 측정하면 두 축의 직교성(마운트 기계 오차)과 현재 경통의 시간각 위치까지 알 수 있다.

**센서 정확도에 따른 한계 (중요)**

| 성분 | 사용하는 센서 | 예상 정확도 | 판단 |
|---|---|---|---|
| 극축 **고도** 오차 | 중력(가속도계) | ±0.3~1° | 쓸 만함 |
| 극축 **방위** 오차 | 나침반(지자기) | ±5~15° | **부정확** |
| (참고) 자북↔진북 차이 | — | 한국 편각 약 −8~9° | 반드시 보정해야 함 (안드로이드 절대 방위는 자북 기준) |

→ **방위는 나침반으로 정하지 말고 별 1개로 확정하는 것을 권장한다.** 축 측정 후 밝은 별 하나를 맞추면(기존 정렬 기능 재사용) 자이로 좌표계와 하늘의 관계가 정해진다. 그러면 나침반 없이 방위 오차를 계산할 수 있다.

**기대 정확도:** 약 ±0.5~1°
- 안시 관측, 저배율 추적, 디지털 세팅서클(ΔRA/ΔDec 안내)에는 충분하다.
- 사진 촬영용(각분 단위) 극축 정렬은 폰 센서로는 불가능하다. 플레이트 솔빙이 필요하며 이 앱의 범위를 벗어난다. 화면에도 이렇게 명시하는 것을 권장한다.

**제안 순차 단계 (적도의 모드 흐름)**

1. **준비:** GPS 위치 확인(위도 필수), 마운트를 대략 북쪽으로 놓고 위도 눈금 설정 안내
2. **적경축 측정:** 폰을 경통에 고정 → 적위 잠금, 적경 클램프 해제 → 안내에 따라 적경축을 천천히 60~90° 왕복
   - 앱이 회전량, 측정 품질(흔들림, 샘플 수), 회전축 일관성을 실시간으로 표시
3. **고도 오차 표시:** "극축이 0.8° 낮습니다 — 고도 나사를 올리세요" (방위는 나침반 기준 *참고치*로만 표시)
4. **별 1개 정렬:** 밝은 별을 망원경 중앙에 맞추고 탭 → **방위 오차 확정** → "극축을 동쪽으로 1.5°" 안내 → 조정 후 2~4단계 재측정으로 확인
5. **(선택) 적위축 측정:** 적경 잠금 후 적위축만 회전 → 직교성·기계 오차 점검
6. **탐색:** 목표 천체를 선택하면 **ΔRA / ΔDec**("적경을 동쪽으로 12°, 적위를 +3°") 안내
   - 적도의에서는 이 안내가 호핑보다 직관적이다.
   - 6월에 구현했다가 되돌린 커밋(`088f820`)의 ΔRA/ΔDec 역변환 공식과 2성 정렬 코드를 재사용할 수 있다.

**구현 시 주의**
- 측정 중에는 v20 평활화 필터를 끄고 원시 센서값을 쓴다. 평활화 지연이 축 추정을 왜곡한다.
- 회전량이 30° 미만이면 축 추정이 불안정하다. 최소 회전량에 도달해야 "측정 완료"로 처리한다.
- 폰 거치대가 흔들리면 오차가 커진다. 샘플 분산으로 "거치대 흔들림" 경고를 띄운다.
- 자이로 드리프트는 1~2분 측정에서는 무시할 수준이다. 측정은 짧게 끝내도록 유도한다.

**권장 개발 단계**

| 단계 | 내용 | 기간 |
|---|---|---|
| A | ΔRA/ΔDec 안내 + 2성 정렬 (되돌린 커밋 재활용·재검증) | 1~2일 |
| B | 적경축 회전 측정 → 극축 고도 오차 | 2~3일 |
| C | 별 1개로 방위 오차 확정 + 조정 안내 + 재측정 루프 | 2~3일 |
| D | 적위축 측정·직교성 점검 (선택) | 1일 |

**AR 모드**는 사용자 의견대로 경위대 모드와 같은 계산 경로를 쓰면 된다(②의 "축 선택"만 다름).
